# Manual Remediation Log

Each finding fixed by hand before automating, with the evidence an assessor would ask for: what was checked, what was changed, and how the fix was verified. CAT I findings first.

**Safety rule for authentication and SSH changes:** keep the current session open and confirm a second, fresh login works before closing it. If the new login fails, the open session is used to roll back.

## CAT I

### RHEL-10-600455: Prevent login to accounts with empty passwords

| | |
|---|---|
| **Severity** | CAT I (high) |
| **NIST 800-53** | IA-5(1)(a), IA-5(c), CM-6(a) |
| **Finding** | `pam_unix.so` had the `nullok` option, which accepts an empty password for any account whose password field is blank. |
| **Risk** | No account had an empty password, but if one ever did (by mistake, or because an attacker blanked it), anyone could log in as that user with no password. |

**Check**

```
$ grep nullok /etc/pam.d/system-auth /etc/pam.d/password-auth
/etc/pam.d/system-auth:auth        sufficient   pam_unix.so nullok
/etc/pam.d/system-auth:password    sufficient   pam_unix.so yescrypt shadow nullok use_authtok
/etc/pam.d/password-auth:auth        sufficient   pam_unix.so nullok
/etc/pam.d/password-auth:password    sufficient   pam_unix.so yescrypt shadow nullok use_authtok

$ sudo authselect current
Profile ID: local
Enabled features: None

$ sudo awk -F: '$2 == "" {print "EMPTY PASSWORD:", $1}' /etc/shadow
(no output: no account currently has an empty password)
```

`system-auth` covers local logins (console, `su`, `sudo`); `password-auth` covers remote ones (SSH). Both had to be fixed.

**Fix**

```
$ sudo authselect enable-feature without-nullok
```

The PAM files are generated by `authselect`. Editing them by hand would be overwritten the next time `authselect` runs, and the finding would come back. Enabling the profile feature makes the change persistent.

**Verify**

```
$ grep nullok /etc/pam.d/system-auth /etc/pam.d/password-auth
(no output)

$ sudo authselect current
Profile ID: local
Enabled features:
- without-nullok
```

A second SSH session logged in successfully and `sudo whoami` returned `root`, confirming both the remote (`password-auth`) and local (`system-auth`) paths still work. Targeted rescan result: `pass` (see the next finding for the command).

### RHEL-10-700610: Disable SSH access via empty passwords

| | |
|---|---|
| **Severity** | CAT I (high) |
| **NIST 800-53** | AC-17(a), CM-6(a), CM-7(a), CM-7(b) |
| **Finding** | `PermitEmptyPasswords` was not set in any SSH configuration file. |
| **Risk** | SSH already refused empty passwords, but only because of a compiled-in default. Defaults can change between versions, and an assessor can't tell a deliberate setting from an accidental one. The STIG requires security settings to be explicitly configured. |

**Check**

```
$ sudo sshd -T | grep -i permitemptypasswords
permitemptypasswords no            <- effective value is already secure

$ sudo grep -ri permitemptypasswords /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
/etc/ssh/sshd_config:#PermitEmptyPasswords no    <- only a comment documenting the default

$ sudo ls -l /etc/ssh/sshd_config.d/
-rw-------. 1 root root 412 Oct  7 20:00 40-redhat-crypto-policies.conf
-rw-------. 1 root root 307 Oct  7 20:00 50-redhat.conf
```

The SSH config files are readable only by root (`-rw-------`), which is itself a STIG requirement.

**Fix**

```
$ sudo tee /etc/ssh/sshd_config.d/00-complianceascode-hardening.conf > /dev/null <<'EOF'
# DISA STIG RHEL-10-700610: SSH must not allow empty passwords
PermitEmptyPasswords no
EOF
$ sudo chmod 600 /etc/ssh/sshd_config.d/00-complianceascode-hardening.conf
$ sudo sshd -t && echo "config OK"
config OK
$ sudo systemctl reload sshd
```

- **Why a drop-in starting with `00-`:** `sshd` uses the *first* value it reads for each setting and reads drop-ins in alphabetical order, so `00-` takes precedence over Red Hat's `40-` and `50-` files.
- **Why this filename:** it's the file the SCAP Security Guide's automated remediation writes to, so the later Ansible run updates this file instead of creating a conflicting one.
- **Why `sshd -t` first:** it validates syntax. Reloading SSH with a broken config can lock out remote access.

**Verify**

```
$ sudo sshd -T | grep -i permitemptypasswords
permitemptypasswords no
```

After the reload, a fresh SSH session from a second terminal logged in successfully before the original session was closed.

Targeted rescan of both CAT I rules fixed so far:

```
$ sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig \
    --rule xccdf_org.ssgproject.content_rule_no_empty_passwords \
    --rule xccdf_org.ssgproject.content_rule_sshd_disable_empty_passwords \
    /usr/share/xml/scap/ssg/content/ssg-rhel10-ds.xml

Title   Prevent Login to Accounts With Empty Password
Rule    xccdf_org.ssgproject.content_rule_no_empty_passwords
Result  pass

Title   Disable SSH Access via Empty Passwords
Rule    xccdf_org.ssgproject.content_rule_sshd_disable_empty_passwords
Result  pass
```

### RHEL-10-700960 and RHEL-10-700950: Disable Ctrl-Alt-Del reboot and burst action

| | |
|---|---|
| **Severity** | CAT I (high), both |
| **NIST 800-53** | AC-6(1), CM-6(a) |
| **Finding** | Pressing Ctrl-Alt-Del on the console rebooted the server immediately, with no login. Separately, systemd's burst action (7 presses within 2 seconds) was set to `reboot-force`. |
| **Risk** | Anyone with console access, or an accidental keypress, could take the server down. `reboot-force` skips the clean shutdown (services aren't stopped, filesystems aren't unmounted cleanly), which risks data corruption. The burst action fires even when the normal mapping is disabled, so both settings must be fixed. |

**Check**

```
$ systemctl is-enabled ctrl-alt-del.target
alias

$ ls -l /etc/systemd/system/ctrl-alt-del.target /usr/lib/systemd/system/ctrl-alt-del.target
/etc/systemd/system/ctrl-alt-del.target -> /usr/lib/systemd/system/reboot.target
/usr/lib/systemd/system/ctrl-alt-del.target -> reboot.target

$ systemctl show --property=CtrlAltDelBurstAction
CtrlAltDelBurstAction=reboot-force
```

`ctrl-alt-del.target` is an alias for `reboot.target`. The `/usr/lib` link is the vendor default; the `/etc` link (created by the installer) is the admin layer, which takes precedence.

**Fix: RHEL-10-700960 (normal mapping)**

```
$ sudo systemctl disable ctrl-alt-del.target
Removed '/etc/systemd/system/ctrl-alt-del.target'.
$ sudo systemctl mask ctrl-alt-del.target
Created symlink '/etc/systemd/system/ctrl-alt-del.target' → '/dev/null'.
```

Masking points the unit at `/dev/null`, so nothing can start it: not the keypress, not another unit, not an admin by accident. That is stronger than `disable`, which only stops it from starting automatically.

**Fix: RHEL-10-700950 (burst action)**

The official remediation script appends `CtrlAltDelBurstAction=none` to `/etc/systemd/system.conf`. On RHEL 10 that file doesn't exist: newer systemd ships its defaults in `/usr/lib/systemd/system.conf` and leaves `/etc` for admin overrides. Appending to the missing file would create one with no `[Manager]` section header, and systemd would ignore the setting. The override was created with the header instead:

```
$ sudo tee /etc/systemd/system.conf > /dev/null <<'EOF'
# DISA STIG RHEL-10-700950: disable the Ctrl-Alt-Del burst reboot
[Manager]
CtrlAltDelBurstAction=none
EOF
$ sudo systemctl daemon-reload
```

**Verify**

```
$ systemctl show --property=CtrlAltDelBurstAction
CtrlAltDelBurstAction=none

$ sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig \
    --rule xccdf_org.ssgproject.content_rule_disable_ctrlaltdel_reboot \
    --rule xccdf_org.ssgproject.content_rule_disable_ctrlaltdel_burstaction \
    /usr/share/xml/scap/ssg/content/ssg-rhel10-ds.xml

Title   Disable Ctrl-Alt-Del Burst Action
Result  pass

Title   Disable Ctrl-Alt-Del Reboot Activation
Result  pass
```

**Live test:** Ctrl-Alt-Del was sent 9 times from the Proxmox console, including about 7 presses within 2 seconds (the burst threshold). The server stayed up, and systemd logged a refusal for each press:

```
$ sudo journalctl -b --since "-5 min" | grep -i ctrl-alt-del

Oct 30 14:50:47 stig01.home.arpa systemd[1]: Failed to enqueue replace-irreversibly job for ctrl-alt-del.target: Unit ctrl-alt-del.target is masked.
Oct 30 14:50:49 stig01.home.arpa systemd[1]: Failed to enqueue replace-irreversibly job for ctrl-alt-del.target: Unit ctrl-alt-del.target is masked.
```

The same journal search also showed `sudo` recording each command used for this fix (user, terminal, working directory, full command line), which is the accountability trail the audit (AU) controls build on.

### RHEL-10-001040: Enable GPG signature checks for local packages

| | |
|---|---|
| **Severity** | CAT I (high) |
| **NIST 800-53** | CM-11(a), CM-11(b), CM-5(3), CM-6(a), SA-12, SA-12(10) |
| **Finding** | `localpkg_gpgcheck` was not set, so it defaulted to off. |
| **Risk** | `dnf` verified signatures on packages downloaded from Red Hat's repositories (`gpgcheck=1`), but not on `.rpm` files installed directly from disk. A tampered or malicious RPM from an email, download, or file share would be installed as root with no check of who built it: a supply-chain risk. |

**Check**

```
$ cat /etc/dnf/dnf.conf
[main]
gpgcheck=1
installonly_limit=3
clean_requirements_on_remove=True
best=True
skip_if_unavailable=False

$ sudo dnf config-manager --dump | grep -i gpgcheck
gpgcheck = 1
localpkg_gpgcheck = 0        <- effective value: off
repo_gpgcheck = 0
```

**Fix**

```
$ sudo dnf config-manager --save --setopt=localpkg_gpgcheck=1
```

Using `dnf`'s own config command instead of editing the file by hand avoids typos and duplicate entries.

**Verify**

```
$ cat /etc/dnf/dnf.conf
[main]
gpgcheck=1
installonly_limit=3
clean_requirements_on_remove=True
best=True
skip_if_unavailable=False
localpkg_gpgcheck=1

$ sudo dnf config-manager --dump | grep -i localpkg_gpgcheck
localpkg_gpgcheck = 1

$ sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig \
    --rule xccdf_org.ssgproject.content_rule_ensure_gpgcheck_local_packages \
    /usr/share/xml/scap/ssg/content/ssg-rhel10-ds.xml

Title   Ensure gpgcheck Enabled for Local Packages
Result  pass
```

### RHEL-10-600000 and RHEL-10-600010: GRUB bootloader password and non-default admin username

| | |
|---|---|
| **Severity** | CAT I (high), both |
| **NIST 800-53** | CM-6(a) |
| **Finding** | GRUB had no password, and its admin (superuser) name was the default `root`. |
| **Risk** | Anyone at the console could press `e` at the boot menu, add `rd.break` or `init=/bin/bash` to the kernel line, and boot into a root shell with no password. A GRUB password closes that path. A non-default username means an attacker also has to guess the account name. |

The GRUB admin username is shown here as `<grub-admin>`. It's kept out of this repo on purpose, since being hard to guess is the point of RHEL-10-600010.

**Safety:** a Proxmox snapshot (`before-grub`) was taken first, since a mistake here can leave the system unable to boot or permanently locked out of boot-entry editing.

**Check**

```
$ sudo cat /etc/grub.d/01_users
#!/usr/bin/sh -e
cat << EOF
if [ -f \${prefix}/user.cfg ]; then
  source \${prefix}/user.cfg
  if [ -n "\${GRUB2_PASSWORD}" ]; then
    set superusers="root"
    export superusers
    password_pbkdf2 root \${GRUB2_PASSWORD}
  fi
fi
EOF

$ sudo ls -l /boot/grub2/user.cfg
ls: cannot access '/boot/grub2/user.cfg': No such file or directory
```

`01_users` generates GRUB's user section: if `user.cfg` holds a password hash, it makes `root` the superuser and gives `root` that password. With no `user.cfg`, GRUB had no password at all.

**Fix: rename the GRUB admin (RHEL-10-600010)**

```
$ sudo cp -p /etc/grub.d/01_users /root/01_users.orig
$ GRUBUSER=<grub-admin>
$ sudo sed -i "s/set superusers=\"root\"/set superusers=\"$GRUBUSER\"/; s/password_pbkdf2 root /password_pbkdf2 $GRUBUSER /" /etc/grub.d/01_users
```

- **Both lines must change.** The STIG fix text only mentions the `set superusers=` line. Changing only that line makes `<grub-admin>` the superuser while the password stays attached to `root`, so no one can authenticate and boot-entry editing is locked out until the system is repaired from rescue media.
- **The backup goes outside `/etc/grub.d/`.** `grub2-mkconfig` runs every executable file in that directory, so a copy left there (permissions preserved by `-p`) would also run and produce a second, conflicting user block.

**Fix: set the password (RHEL-10-600000) and rebuild the config**

```
$ sudo grub2-setpassword
Enter password:
Confirm password:

$ sudo grub2-mkconfig -o /boot/grub2/grub.cfg
Generating grub configuration file ...
Adding boot menu entry for UEFI Firmware Settings ...
done
```

- `grub2-setpassword` stores a PBKDF2-SHA512 hash in `/boot/grub2/user.cfg`, not the password itself. The GRUB password is different from any login password.
- On RHEL 9 and later, the real config is `/boot/grub2/grub.cfg` even on UEFI systems; the file on the EFI partition is a stub that points to it. Writing the config to the EFI partition instead is a common way to break booting.

**Verify**

```
$ sudo ls -l /boot/grub2/user.cfg
-rw-------. 1 root root 298 Oct 30 15:00 /boot/grub2/user.cfg

$ sudo grep -c GRUB2_PASSWORD=grub.pbkdf2.sha512 /boot/grub2/user.cfg
1

$ sudo grep -A3 superusers /boot/grub2/grub.cfg
    set superusers="<grub-admin>"
    export superusers
    password_pbkdf2 <grub-admin> ${GRUB2_PASSWORD}

$ sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig \
    --rule xccdf_org.ssgproject.content_rule_grub2_password \
    --rule xccdf_org.ssgproject.content_rule_grub2_admin_username \
    /usr/share/xml/scap/ssg/content/ssg-rhel10-ds.xml

Title   Set the Boot Loader Admin Username to a Non-Default Value
Result  pass

Title   Set Boot Loader Password in grub2
Result  pass
```

**Live test:** the VM was rebooted from Proxmox and the GRUB menu was stopped with an arrow key.

- Pressing `e` on the default entry no longer opens the editor. GRUB asks for credentials first:

  ![GRUB asking for a username before allowing boot-entry edits](images/05-grub-username-prompt.png)

- Logging in as `<grub-admin>` with the GRUB password opened the editor for the `6.12.0-211.69.1` entry. Nothing was changed; Esc returned to the menu.
- Selecting the default entry and pressing Enter booted normally to the login prompt with no GRUB password requested. The password protects editing and the GRUB command line, not ordinary boots.

The editor screen also showed the kernel command line that the password now protects: `linux ($root)/vmlinuz-6.12.0-211.69.1.el10_2.x86_64 root=/dev/mapper/rhel_stig01-root ro ... fips=1`. Before the fix, appending `rd.break` there would have given a root shell.
